# Спецификации изменений

Здесь фиксируем будущие изменения с новой логикой, данными, правами или несколькими
пользовательскими сценариями. Процесс и самостоятельность разработчика описаны
в [AGENTS.md](../AGENTS.md). Мелкая правка может обойтись без spec.

## Минимальный формат

Обычно достаточно **одного** `YYYY-MM-DD-short-name.md` по [_template.md](_template.md).
Название отражает изменение; дата помогает найти его, отдельная нумерация не нужна.
Требования, короткий план, приёмка и результат помещаются вместе. Неприменимые
пункты удаляются. Не нужен отдельный файл для каждого шага или каждой проверки.

Только если один документ перестал быть удобным, используй
`YYYY-MM-DD-short-name/spec.md`, а план или список крупных задач вынеси рядом.
Оставь из spec ссылки на эти файлы; не дублируй содержание.

## Как читать и поддерживать

- В начале: статус, источник требований (краткое решение пользователя или ссылка
  на доступный документ/PR), связанные модульные документы и последнее обновление.
  Частные данные поездки и секреты не помещать в spec.
- `черновик` — есть существенные открытые вопросы; независимую часть можно делать.
  `в работе` — требований достаточно, реализация продолжается. `готово` — запрос
  выполнен и результат/проверки записаны. `заменена` — есть ссылка на новое решение.
  Это отметки состояния, а не последовательность обязательных согласований.
- При изменении требований обновляй ожидаемое поведение и коротко поясняй важный
  выбор. Не оставляй отменённый вариант действующим требованием.
- При паузе запиши оставшуюся работу и конкретный следующий шаг. При завершении
  разделяй выполненные проверки и предложенные, реализацию и публикацию.
- После реализации актуальное поведение переносится в существующий документ
  модуля; spec сохраняет контекст изменения и ссылается на него. Не поддерживай
  две расходящиеся копии описания всей функции.
- Старые документы `docs/PLANNING.md`, `docs/WEB_PUSH_TIMEZONES.md` и другие остаются
  описанием реализованной системы. Переписывать их в ретроспективные spec не нужно.

## Текущее состояние

Переход на Lightweight SDD меняет инструкции и организацию документации,
не продукт. Открытых продуктовых spec пока нет; кандидаты следующих задач —
в [HANDOFF](../docs/HANDOFF.md). Их наличие не является разрешением начать работу.

Чтобы продолжить задачу в новом чате: прочитать AGENTS → HANDOFF → нужную spec
и документы модуля, затем сверить ветку и код. Отдельный SDD-фреймворк не нужен.
