# Управление планом через чат

Перед созданием, изменением или перепланированием задач прочитай [единые правила задач](PLANNING_RULES.md).

1. Читать актуальный /api/planning и данные связанных мест; не полагаться на старую переписку.
2. При изменении рейса/маршрута проследить planning_dependencies, связанные решения, бронирования и пункты маршрута.
3. Проверять актуальность первоисточников для новых фактов. Сроки и приоритеты оформлять по единым правилам задач.
4. Показать предложение было → станет с причиной для каждой записи. Без согласования не запускать каскад изменений.
5. Применять изменения через API с актуальными version. Пользовательскую note не заменять подготовленным description.
6. Опции решений и связи задавать структурно через API. Простой affects_visit означает реальное условие посещения; обычная бронь — информационная связь. Общие места вариантов указывать в каждом подходящем варианте.
7. Проверять отсутствие циклов зависимостей. Зависимости мягкие; автопереноса дат нет.
8. Не удалять альтернативы при выборе; только keep/hide. Не восстанавливать удалённые места. Учитывать другие решения до снятия maybe.
9. Перед миграцией/массовыми изменениями сделать SQLite snapshot. После — проверить версии, количество записей, FK и сохранность заметок.
10. Все продуктовые права editor = admin; управление пользователями — только admin. Личные Web Push выполняет существующий backend; не добавлять отдельные фоновые службы или ИИ-сервисы без запроса.

## Первичное наполнение

`node server/import-planning.mjs EXISTING_DATABASE MANIFEST ACTOR_ID` — только с активным существующим editor/admin. CLI предварительно сохраняет SQLite snapshot (0600). Manifest содержит namespace и items с уникальными key; dependencies ссылаются на key. Порядок проверяется на циклы до записи. ID детерминированы namespace/key; повторный запуск пропускает существующие записи и не перезаписывает пользовательские правки. Личный manifest хранится вне Git и public/. Миграция схемы выполняется отдельно после резервной копии.

Пакет применяется одной транзакцией через `applyPlanningChange`, общий с HTTP путь валидации и записи. Ошибка любой записи откатывает весь пакет, включая связанные статусы и историю. Для отдельных записей внутри пакета используются savepoint. Удалённые ранее записи пропускаются по истории удаления и не восстанавливаются.

## Личный реестр и роли чатов

Личная Google Sheets используется для обсуждения мест и очереди предложений.
Это снимок, не автоматическая синхронизация и не замена текущему API. Частная
ссылка, детали билетов и отчёты — в `.local/TRIP_CONTEXT.md` основного checkout;
их не публикуют в spec или Git. Планирование частей поездки вне Тайваня требует
отдельного запроса. Правила ниже сохраняют договорённости 1 и 5 ноября 2026.

Перед работой прочитай актуальную вкладку книги «Правила для ассистентов»:
в ней хранится единственная полная матрица разрешённых столбцов. Другие чаты
готовят предложения только в разрешённых полях листа «Места». Системные ID,
текущий статус/видимость, версии, связи, календарь и прочие листы ведёт
координатор синхронизации. Это обязанность назначенного пользователем чата,
а не дополнительная роль аккаунта сайта; новый чат не получает её только
потому, что прочитал этот документ.

- Для отбора очереди сначала читать ID, название и AN «Синхронизация с картой», затем полные строки ожидающих изменений. Допустимые метки: «Новое», «Изменено», «Синхронизировано».
- Автор ставит «Новое»/«Изменено» вместе со смысловой правкой. У нового предложения серверный ID и системные поля пустые; у существующего сохраняются. План не подменяет текущие статус/видимость. Только координатор завершает очередь после записи и обратной сверки.
- Перед сравнением читать свежие `/api/export` и `/api/planning`. Сопоставлять места по ID, сохранять пользовательские заметки, предложения, ещё не добавленные строки, все связи и пересечения решений.
- Изменение таблицы само по себе не разрешает запись на сайт, удаление места или перенос календаря. При уже согласованном пакете не требовать повторного подтверждения каждого поля; перед записью проверить актуальные версии и существенные расхождения.
- Исчезнувшие строки и другие листы проверять отдельно по задаче: AN не является полным журналом изменений. Копирование часов с сайта не считается новой проверкой источника; дата сверки отличается от даты проверки сведений.

## Массовая сверка координатором

1. Повторно проверить очередь, состав пакета, уникальность ID и серверные версии. Показать ещё не согласованные последствия, особенно решения/переносы. Не загружать полную production-базу с аккаунтами на Mac ради сверки: backup и репетиция выполняются на VPS; для таблицы достаточно нужных диапазонов.
2. На согласованной копии проверить количество записей, FK, сохранность заметок и доступа, отсутствие непредусмотренных удалений. Решения применять штатным обработчиком с предпросмотром и версиями; альтернативы скрывать с сохранением истории.
3. Подтверждённое проживание отражать посещением с подтверждёнными датами, ещё не купленный транспорт — открытой задачей. Использовать существующую категорию «Жильё» без дубликата. Запись выполнить согласованным пакетом с транзакционными гарантиями и backup.
4. Перечитать сервер, обновить текущие значения/версии/связи в реестре и сравнить результат. Метки AN «Синхронизировано» выставлять последними. Подробный отчёт остаётся частным.
