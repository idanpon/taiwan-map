# Управление планом через чат

1. Читать актуальный /api/planning и данные связанных мест; не полагаться на старую переписку.
2. При изменении рейса/маршрута проследить planning_dependencies, связанные решения, бронирования и пункты маршрута.
3. Различать внешние фиксированные сроки (fixed_external + source_urls), согласованные даты и предположения. Проверять актуальность первоисточников для новых фактов; не выдавать предполагаемые даты за подтверждённые.
4. Показать предложение было → станет с причиной для каждой записи. Без согласования не запускать каскад изменений.
5. Применять изменения через API с актуальными version. Пользовательскую note не заменять подготовленным description.
6. Опции решений и связи задавать структурно через API. Простой affects_visit означает реальное условие посещения; обычная бронь — информационная связь. Общие места вариантов указывать в каждом подходящем варианте.
7. Проверять отсутствие циклов зависимостей. Зависимости мягкие; автопереноса дат нет.
8. Не удалять альтернативы при выборе; только keep/hide. Не восстанавливать удалённые места. Учитывать другие решения до снятия maybe.
9. Перед миграцией/массовыми изменениями сделать SQLite snapshot. После — проверить версии, количество записей, FK и сохранность заметок.
10. Все продуктовые права editor = admin; управление пользователями — только admin. Не создавать фоновые уведомления или ИИ-сервисы.

## Первичное наполнение

`node server/import-planning.mjs EXISTING_DATABASE MANIFEST ACTOR_ID` — только с активным существующим editor/admin. CLI предварительно сохраняет SQLite snapshot (0600). Manifest содержит namespace и items с уникальными key; dependencies ссылаются на key. Порядок проверяется на циклы до записи. ID детерминированы namespace/key; повторный запуск пропускает существующие записи и не перезаписывает пользовательские правки. Личный manifest хранится вне Git и public/. Миграция схемы выполняется отдельно после резервной копии.
