# Порядок размещения

Основная схема: GitHub Pages на github.io отдаёт интерфейс, API работает на независимом HTTPS hostname VPS под systemd. AUTH_MODE=bearer, точный CORS allowlist и Authorization; cookie и custom domain для интерфейса не нужны. По одной статической странице нельзя обеспечить серверное хранение и проверку пароля.

## GitHub

- Новый отдельный репозиторий, подключённое GitHub-приложение должно иметь к нему доступ.
- Загрузить исходники и выбрать Pages → GitHub Actions.
- Workflow тестирует код и публикует только dist/. Не загружать env, приватные отчёты, экспорты или базу.
- Основные публичные настройки хранятся в pages.config.json: apiBase, authMode, customDomain. Переменные PAGES_API_BASE / PAGES_AUTH_MODE / PAGES_CUSTOM_DOMAIN могут их переопределить. API URL — HTTPS, без завершающего слеша; authMode=bearer, customDomain пустой.
- Custom domain в настройках Pages оставить пустым. Если домен уже был сохранён, удалить его. Проверить HTTPS адрес API до указания его в сборке.

## VPS

- Подтвердить Node 24+, путь к node и свободный локальный порт. Не обновлять runtime других служб вслепую.
- Создать отдельного системного пользователя taiwan-map, код /opt/taiwan-map, данные /var/lib/taiwan-map, env /etc/taiwan-map.env root:root 0600.
- Проверить и установить server/taiwan-map.service. Порт доступен только на loopback. В checkout выполнить `npm ci --omit=dev --ignore-scripts` с выбранным Node runtime. Для проверки Telegram JWT используется `jose`.
- Задать APP_PASSWORD_HASH через stdin-helper. Для уже установленной службы: python3 server/configure-pages-env.py https://API-HOST сохраняет пароль и включает AUTH_MODE=bearer / FRONTEND_ORIGIN=https://idanpon.github.io; перед применением создаётся копия env с правами 0600.
- Сначала изучить существующий reverse proxy. Для независимого API добавить отдельный virtual host технического hostname. Старый server/Caddy-route.snippet относится к отложенному варианту со своим доменом и сейчас не применяется. Удалить ранее добавленный маршрут /taiwan/* на домене знакомого после проверки конфига. Он не заменяет конфиг nginx/Caddy. При наличии внешнего TCP/SNI demux нужно отдельно проверить client-IP forwarding; не включать PROXY protocol глобально.
- Пока service остановлен, импортировать финальный экспорт в пустую SQLite через server/import.mjs. Не коммитить экспорт. Старый сайт до приёмки оставить активным.
- Запустить службу, проверить health, CORS, пароль, сохранение после рестарта, экспорт и доступ с Safari/iPhone. Убедиться, что существующие службы продолжают работать.
- Настроить копирование SQLite-снимков за пределы VPS и проверить восстановление. Локальные снимки не защищают от потери сервера.

## Если чего-то ещё нет

Если адрес API не задан в pages.config.json или переменных, сборка Pages намеренно показывает сообщение, что сервер данных не подключён, и блокирует вход. Она не сохраняет статусы в localStorage. Ни репозиторий, ни DNS, ни VPS не создаются и не изменяются самими этими исходниками — нужны соответствующие административные действия.

## Обновление авторизации

Для уже работающего проекта следовать [порядку перехода на отдельные аккаунты](ACCOUNTS.md): предварительный SQLite snapshot, проверка миграции, установка зависимостей, backend, затем Pages. Существующие unit и proxy сохраняются. Первый admin настраивается внутри сайта; пароли не передаются в чат.
