# Размещение и обновление

GitHub Pages публикует интерфейс из `main`; API работает отдельно под systemd
на VPS. Frontend-коммит не обновляет сервер. Рефакторинг из
`codex/audit-refactor` объединён через PR #43; фактическое состояние выпуска
зафиксировано в [AUDIT_REFACTOR.md](AUDIT_REFACTOR.md).

## Обычный выпуск существующего проекта

Для нового плагина ChatGPT дополнительно следовать [порядку подключения](CHATGPT_PLUGIN.md#публикация-и-личное-подключение): миграция 0010, выключенная по умолчанию возможность, точные OAuth callback и маршруты discovery. Этот документ не означает разрешение на production.

1. Проверить ветку, diff, lockfile и список изменённых SQL-миграций. Выполнить
   установку закреплённых зависимостей при необходимости; выбрать локальные
   проверки по изменению и риску согласно [AGENTS.md](../AGENTS.md). Для кода,
   затрагивающего сборку, проверить `npm run build:pages` на Node 24+.
   Для данных/прав нужны проверки сохранности, отказов и отката; для UI —
   затронутые пользовательские сценарии. Штатный CI по-прежнему выполняет
   `npm ci --ignore-scripts`, `npm test` и сборку, его не отключают ради SDD.
2. Для backend сначала сохранить согласованный SQLite snapshot и проверить
   `integrity_check`/`foreign_key_check` на копии. Это особенно важно перед
   миграциями и массовой записью. JSON-экспорт не заменяет полный backup:
   он не содержит паролей, сессий, passkeys, устройств и личных напоминаний.
3. После разрешения на production установить проверенную ревизию backend в
   существующий `/opt/taiwan-map`, выполнить установку закреплённых зависимостей
   и обновить существующую службу. Схема проверяется и мигрируется при старте
   `server/index.mjs`; каждую новую миграцию сначала проверяют на копии базы.
   Не менять попутно proxy, DNS, env и Node других служб.
4. Проверить health, чтение, вход, роли, сохранение, версии записей и журналы
   службы без вывода секретов. При изменении контракта сначала выпускают
   совместимый backend, затем frontend. Не применять старые локальные deploy-скрипты
   без сверки с текущими исходниками.
5. Опубликовать frontend через штатный GitHub Actions workflow из `main`.
   Он проверяет код и загружает только `dist/`. Проверить уже опубликованную
   карту и календарь, включая версионированные модули и CSP.

Откат кода — возврат к предыдущей проверенной ревизии. Откат схемы не выполняется
автоматически: восстановление snapshot требует остановки записи и согласования
потери изменений, сделанных после него.

### Репетиция перехода планировщика в model3

Этапы 1–6 реализованы локально, выпуск не выполнялся. `0014`–`0019` добавляют
таблицы/поля; поездка остаётся model2. Новый UI выбирается по модели поездки
и capabilities backend. Разрешения на выпуск и переход production нет.
Готовность/брони, переносы, варианты, файлы, MCP/import и напоминания по срокам
связаны с общим движком. `0016` не меняет прежние даты/версии и не утверждает слоты.
`0017` сохраняет прежние options и не превращает legacy решения в route_segment.

```sh
node server/rehearse-planning-upgrade.mjs SOURCE.sqlite NEW_OUTPUT_DIRECTORY ACTOR_ID
```

Источник открывается только для чтения. Выходной каталог обязан быть новым;
SQLite backup создаёт в нём `upgraded.sqlite`, после чего только к копии
применяются SQL-миграции и `upgradePlanningModel`. ACTOR_ID — действующий
editor/admin (либо прежний owner) этой поездки. Каталог 0700, база/отчёт 0600.
Отчёт `report.json` содержит числа и результаты проверок без записей поездки:
сохранность исходника/старых полей, FK/integrity и повтор перехода без дублей.
Ошибка оставляет исходник неизменным; проблемная копия остаётся для разбора.
Дополнительно проверяется промежуточный результат SQL: прежние поля сохранены,
`schema_model` не изменился до явного перехода. Это позволяет выпустить новый
backend с прежней моделью поездки. Для полного выпуска предпочтительна общая
репетиция ниже: она включает эту проверку и восстановление файлов.

Автотесты используют синтетические SQLite-базы, включая схему до `0014`,
жильё/транспорт, личные напоминания и историю отправок. Добавление `0016`
проверено отдельно на backup заполненной model3-базы этапа 2: старые строки,
версии и исходник сохранены, FK/integrity и повтор миграции успешны.
Добавление `0017` также проверено на backup заполненной model3-базы этапа 3:
сохранены все прежние колонки/версии, legacy options, услуги и исходник; FK,
integrity и повтор миграции успешны. Ошибка внутри пакетной записи вариантов
откатывает изменения, историю и квитанцию; повтор успешного apply идемпотентен.
Перед будущим выпуском
обязательна отдельная репетиция на актуальном согласованном backup production.
Проверка тестовых данных её не заменяет. Не откатывать произвольный старый writer
поверх model3 и не удалять таблицы; нужен совместимый backend/read-only режим
либо отдельно согласованное восстановление исходного backup.

### Общая репетиция выпуска и восстановления

```sh
node server/rehearse-planning-release.mjs SOURCE.sqlite_OR_BUNDLE NEW_OUTPUT_DIRECTORY ACTOR_ID
```

Вход — согласованный неизменяемый SQLite backup либо каталог bundle, созданный
`document-backup.mjs`. Рабочий DATABASE_PATH не является входом для выпуска.
Если есть хотя бы один ready asset, требуется bundle: одна SQLite отклоняется.
Выходной каталог новый и вне исходного bundle; каталоги 0700, файлы 0600.
Никакие службы и настройки среды команда не переключает.

| Результат | Назначение |
|---|---|
| `rollback/database.sqlite`, `rollback/documents/` | Исходная модель и файлы до применения SQL/перехода. Для bundle действуют обычные правила restore: незавершённые uploads истекают, leases очищаются |
| `candidate/upgraded.sqlite`, `candidate/documents/` | SQL-миграции и явный переход, сохранность прежних полей/версий, FK/integrity, повтор без дублей, проверенные возможности нового UI |
| `candidate-backup/` | Полный bundle новой модели, включая текущие, исторические и ещё личные ready assets |
| `recovered/database.sqlite`, `recovered/documents/` | Проверенное восстановление новой модели, пригодное для последующего контролируемого переключения |
| `report.json` | Числа и проверки, fingerprint источника, SQL hashes, policy version; без содержимого записей/файлов |

До полного успеха присутствует `INCOMPLETE`; его нельзя удалять вручную ради
продолжения выпуска. При ошибке сохранить каталог для разбора, устранить причину
и повторить в новом. Повреждённые/отсутствующие файлы, неверное проживание,
недостаточная роль и изменения источника останавливают проверку. При recovery
сравниваются все таблицы: допустимы только стандартное истечение незавершённых
uploads и удаление operational leases, остальные данные должны совпасть.

На синтетических model2 до 0014 и заполненной model3 проверены полный переход,
документы/история/личные файлы, восстановление, ошибочные входы и совместимость.
CLI отдельно прошёл на bundle локальной демонстрации. Это не репетиция текущих
production-данных. Полный прогон от 14 ноября: 357 тестов, сборка успешна.

### Порядок будущего выпуска «Маршрута и подготовки»

1. После разрешения на выпуск выбрать проверенную ревизию, получить актуальный
   согласованный backup и прогнать общую репетицию. Для старой схемы до 0018
   достаточно SQLite backup; для имеющихся файлов обязателен bundle. При отказе
   разбирать данные копии, не править рабочую поездку по догадке.
2. Сначала обновить backend и SQL по обычному порядку выше, сохранив model2.
   Проверить вход editor/viewer, приватность, чтение и существующий календарь.
   При наличии `0019` проверить историю reminder generations/deliveries.
3. Затем выпустить Pages. Новый клиент продолжает показывать прежний план,
   пока поездка model2. Workflow автоматически сверяет SHA-256 всех основных
   HTML/JS/CSS/webmanifest, включая модули маршрута (сейчас 88 файлов), а также
   ожидаемую ревизию. Проверить, что новый клиент загрузился из Pages/PWA.
4. Для включения model3 остановить службу (включая scheduler) и удерживать
   остановку до переключения. Сделать **новый финальный backup** и повторить
   общую репетицию проверенной ревизией: между этим snapshot и переключением
   не допускаются записи, включая пользователей, фоновые задания и CLI.
   Предварительная репетиция из шага 1 не заменяет финальную копию.
5. Только успешный финальный `recovered/` с отчётом без INCOMPLETE можно
   поместить в закрытый постоянный каталог и назначить существующей службе
   как согласованную пару DATABASE_PATH/DOCUMENT_ROOT. Сохранить прежнюю пару
   и финальный backup, проверить владельца файлов и запустить **ту же совместимую
   ревизию** backend. Это явное включение; запуск приложения сам его не делает.
6. Проверить на опубликованном UI: карточка → подготовка → бронь → скачивание,
   сравнение вариантов без изменения рабочего, preview переноса к фиксированному
   билету, viewer, неизменные заметки/история. Для записей в рабочую поездку
   использовать согласованный полезный сценарий, не оставлять тестовый мусор.
   Отдельно пройти физический iPhone/PWA, установленный MCP и живой Push.

До включения model3 отмена перехода означает оставить новый API с model2.
После включения предпочтительно исправлять совместимый API на месте. Старый
клиент получает ограниченную совместимую выборку и отказ на структурные записи;
это защита кэшированных вкладок, а не полноценный запасной интерфейс model3.
Возврат произвольного старого backend поверх новой схемы не проверен и не является
поддерживаемым откатом. Возврат `rollback/` требует остановки службы и отдельного
согласования потери всех записей после финального snapshot — в том числе новых
файлов, сессий и напоминаний. До такого решения сохранить также текущую полную
копию. Восстанавливать БД и assets одной согласованной парой.

14 ноября пользователь разрешил этот выпуск после успешной репетиции на
актуальной копии рабочей базы, с сохранением backup для отката. Доработка
градиентов, цветов и иконок отслеживается в бэклоге
и не подменяет техническую готовность либо пользовательское согласование.

### Файлы model3 и резервные копии

SQL `0018` добавляется без изменения прежних миграций. Проверена на заполненной
синтетической SQLite-копии этапа 4: прежние колонки/версии, решения/опции,
подтверждённое жильё и исходная база сохранены; FK/integrity и повтор успешны.
Это не репетиция на production. SQLite-only rehearsal проверяет схему,
но не заменяет проверку assets при будущем выпуске.

`DOCUMENT_ROOT` по умолчанию равен `documents/` рядом с DATABASE_PATH.
Это закрытый постоянный каталог: directories 0700, files 0600, вне public/dist;
в контейнере стандартный `/app/data/documents` уже попадает в volume данных.
`DOCUMENT_MAX_BYTES` можно уменьшить с 20 MiB, `DOCUMENT_QUOTA_BYTES` по
умолчанию 512 MiB. Квота включает параллельные незавершённые загрузки и историю.
Параметры — в `.env.example`; действующий env не менялся.
Перед будущим выпуском сверить лимит тела и buffering reverse proxy:
content endpoint должен пропускать 20 MiB и поток до Node. Обычный JSON-лимит
сервера не увеличен; запросы по-прежнему проходят origin/session/membership.

Согласованный backup с файлами создаётся **в новый каталог**:

```sh
node server/document-backup.mjs backup DATABASE.sqlite DOCUMENT_ROOT NEW_BACKUP_DIRECTORY
node server/document-backup.mjs restore BACKUP_DIRECTORY NEW_RESTORE_DIRECTORY
```

Backup содержит database.sqlite, manifest.json и documents/assets. Lease
защищает файлы от GC/discard во время SQLite snapshot и копирования. Включены
все ready assets снимка: общие, архивные и ещё личные; staging bytes не включены.
SHA-256, размер, сигнатура, FK/integrity проверяются. До завершения есть
INCOMPLETE; такой каталог не восстанавливается. При ошибке повторять backup
в новый каталог, сохраняя неудачную копию для разбора.

Restore сверяет manifest с БД и каждый файл до выдачи нового каталога; пишет
во временный соседний каталог и переименовывает его после проверки. Выход —
database.sqlite, documents/ и restore-report.json. Старый каталог не
перезаписывается, служба/production не переключаются. Незавершённые uploads
снимка становятся expired; ready файлы и документы сохраняются.
Переключение DATABASE_PATH/DOCUMENT_ROOT — отдельное действие выпуска.
JSON export и старые SQL-only backup/import скрипты не являются полным
восстановлением model3 с файлами. Нельзя восстановить одну БД, считать работу
завершённой и удалить старое хранилище assets.

При включённом AUTO_BACKUPS model3 использует проверяемые `taiwan-DATE.bundle`,
сохраняя 14 завершённых дневных копий; незавершённые не удаляет автоматически.
Model2 сохраняет прежний SQLite-only режим. GC работает отдельно раз в час
и никогда не удаляет assets с текущими/историческими document-ссылками.
На VPS AUTO_BACKUPS остаётся 0; публикации или настройки сервера не выполнялись.
Копии на том же диске не заменяют внешнее хранение.

## Выпуск фиксированных статусов и новых типов

На VPS перед обновлением снять согласованную SQLite-копию и проверить
назначения статусов во всех `user_place_states`, включая скрытые места
и старые профили. `0011` прекращает запуск при действующем назначении
кастомного статуса. При таком отказе согласовать его переназначение,
сохранив заметки и историю, затем повторить репетицию.

Проверить на копии `0011`, `integrity_check`, `foreign_key_check`, количество
записей и связи, включая напоминания и очередь. Выпустить совместимый API/MCP
раньше Pages. Обновить описание инструментов в подключении ChatGPT при
кэшировании схемы. После подтверждения конкретного предложения провести
[адресное преобразование старых посещений](PLANNING_OPERATIONS.md#преобразование-старых-посещений).
Проверить обратное чтение данных и частный контур жилья. Предыдущий Pages
читает совместимую выборку. Для возврата backend после записей новых типов
сначала подготовить совместимый план отката с учётом уже принятых изменений.

## Выпуск «Лёгкой ясности» и Плана поездки

По решению пользователя проверка удержания, переноса и обычной прокрутки
на физических устройствах iOS и Android проводится после выпуска.
В релизе нет новых SQL-миграций. Сначала сделать и проверить снимок SQLite,
затем обновить API. Новый План передаёт
`timezone_revision` при изменении даты и отмене переноса. Сервер возвращает
409 при устаревшей ревизии, а запросы текущего сайта без поля остаются
совместимыми. Проверка этого контракта на тестовой базе входит в
`tests/planning.test.mjs`.

После проверки API объединить PR в `main`. Этот шаг запускает публикацию
Pages. После неё сверить ревизию и открыть карту, пустой Список, свободный
день в Календаре и карточку записи в обеих темах. Для отката сначала вернуть
прежний frontend. Старый API можно вернуть после проверки доставки отката
Pages, чтобы новые клиенты не потеряли проверку ревизии.

## Надёжность GitHub Pages

Публикации `main` сериализованы и не отменяют уже выполняющийся выпуск.
Для PR сохраняется отмена устаревшей проверки. Ручной запуск с другой ветки
выполняет проверки, но не публикует production. `configure-pages` v6.0.0
и `deploy-pages` v5.0.1 закреплены точными commit SHA и работают на Node 24;
новый deploy action использует увеличение интервала опроса и jitter.

Перед загрузкой артефакта workflow создаёт публичный `release.json`: SHA
коммита и SHA-256 тринадцати основных файлов карты/календаря/ассистента. После успешного
ответа Pages отдельный шаг сверяет публичную ревизию и эти файлы.
При задержке CDN допускается шесть проверок с интервалом 10 секунд;
несовпадение завершает workflow ошибкой. Это проверка доставки, а не подмена
ошибочного deploy успешным HTTP-ответом сайта. В файле нет пользовательских данных.

При `deployment_queued` / `Deployment failed, try again later` сначала
проверить журнал deploy и GitHub Status. Если сборка и артефакт исправны,
после восстановления сервиса повторить только failed jobs: это сохраняет
исходный проверенный артефакт. Не повторять весь build/upload в том же run
без причины и не создавать пустые коммиты для обхода очереди. Если повтор
снова неуспешен, сохранить ID run/артефакта и проверить состояние Pages;
не маскировать ошибку через `continue-on-error`.

6 ноября 2026 повтор failed deploy запуска
[42266830604](https://github.com/idanpon/taiwan-map/actions/runs/42266830604)
завершился `Reported success!` с тем же commit `b11e1e9` и артефактом
`13526843939`, без изменения кода или настроек сайта. Это свидетельствует
о временном сбое обработки Pages; его внутреннюю причину API не раскрыл.
Изменение очереди — защита будущих выпусков, а не доказательство причины
того сбоя. Данные и службы VPS при этой работе не меняются.

## Конфигурация

- Публичные параметры: `pages.config.json` (`apiBase`, `authMode`, `customDomain`).
  `PAGES_API_BASE`, `PAGES_AUTH_MODE`, `PAGES_CUSTOM_DOMAIN` переопределяют их.
  Текущий режим — HTTPS API и bearer, интерфейс на github.io, custom domain пустой.
- В службе используются `AUTH_MODE=bearer` и точный
  `FRONTEND_ORIGIN=https://idanpon.github.io`. Секреты — только в закрытом env;
  значения параметров перечислены в `.env.example`.
- При отсутствии API сборка Pages показывает понятное сообщение и блокирует
  вход; локального суррогата серверных данных нет.
- На действующем VPS `AUTO_BACKUPS=0` сохраняет прежний режим без встроенного
  периодического копирования. В обычном локальном запуске снимки включены по
  умолчанию. Их внешнее хранение и восстановление проверяют отдельно: копия
  на том же VPS не защищает от потери сервера.

## Первоначальное развёртывание (не повторять при обычном обновлении)

Потребуются Node 24+, отдельный пользователь службы, код `/opt/taiwan-map`,
данные `/var/lib/taiwan-map`, env `/etc/taiwan-map.env` с правами 0600, служба
`server/taiwan-map.service` и HTTPS proxy к loopback-порту. Сначала изучают
существующий proxy; `server/Caddy-route.snippet` — пример прежней схемы, не
готовая конфигурация текущего hostname. `TRUST_PROXY=1` допустим только при
доверенном proxy, перезаписывающем `X-Real-IP`.

Первый admin настраивается через защищённый bootstrap согласно
[ACCOUNTS.md](ACCOUNTS.md). Пароли не передают в чат. Legacy map-only импорт
`server/import.mjs` предназначен для пустой базы и не восстанавливает календарь,
план поясов или личные данные. Полное восстановление выполняют из SQLite backup.

Для отдельного репозитория в настройках Pages выбирают GitHub Actions. Env,
базы, `.local/` и частные экспорты никогда не загружают в Pages или Git.

## Passkeys, Web Push и пояса

Миграции `0008_passkeys.sql` и `0009_web_push_timezones.sql` уже входят в текущую
историю схемы. Применённые SQL-файлы не переписывают: runner сверяет их хеши.
См. [PUBLIC_ACCESS_PASSKEYS.md](PUBLIC_ACCESS_PASSKEYS.md) и
[WEB_PUSH_TIMEZONES.md](WEB_PUSH_TIMEZONES.md).

Для первого подключения пушей пару VAPID создают установленным пакетом `web-push`
и сохраняют непосредственно в закрытом env: `PUSH_VAPID_PUBLIC_KEY`,
`PUSH_VAPID_PRIVATE_KEY`, `PUSH_VAPID_SUBJECT`. Пару сохраняют при обновлениях,
не генерируют заново. Отправителю нужен исходящий HTTPS. Без этих параметров
правила напоминаний можно хранить, подключение устройств и отправка недоступны.
Worker и manifest находятся в области приложения Pages. После публикации
проверяют реальное напоминание при закрытом PWA на iPhone и переход в карточку;
автоматические тесты доставки этого не заменяют.
