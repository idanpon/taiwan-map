# Планировщик поездки — спецификация и архитектура

Согласовано 21 октября 2026. Вылет 28.12.2026, пребывание 29.12.2026–09.01.2027.

## Продуктовые правила

- Одна общая поездка, карта и отдельная страница planning.html. Авторизация, тема, пользователи и SQLite общие.
- Admin и editor имеют одинаковые продуктовые права. Только управление пользователями дополнительно доступно admin. Viewer читает.
- Три типа записи: task (задача), decision (решение с вариантами), visit (пункт маршрута, включая переезды и свободное время).
- Описание и пользовательская заметка раздельны. Ответственный необязателен. Все участники редактируют общий план.
- Состояния task/decision: open, in_progress, done, cancelled. Visit: open (запланировано), done (состоялось), cancelled (пропустили).
- Месяц, неделя (понедельник–воскресенье), день и список. При новом входе текущий месяц. Сегодня выделено; кнопка Сегодня возвращает к текущему дню.
- В месяце переполнение раскрывается через «Ещё N» в полный список дня. Неделя на телефоне идёт вертикально. Все списки прокручиваются без ограничения количества.
- Запись периода одна, но видна во все дни периода. Визиты упорядочены внутри дня, время необязательно; повторное посещение — отдельная запись.
- Без даты — отдельная доступная группа «Без срока» со счётчиком.
- Сегодня и текущий период имеют один цвет; скоро (7 дней) — янтарный, просрочено — красный. Цвет дополняется текстом. Завершённые и отменённые не просрочены.
- По умолчанию часовой пояс устройства, ручной выбор хранится в браузере. Даты без времени не сдвигаются; точные моменты хранятся в UTC с исходным поясом. День маршрута остаётся местным днём посещения.
- Не смешивать состояние задачи, посещение, статус места и ярлык бронирования. Изменение visit на done только предлагает сменить статус места.
- Решения фиксирует любой editor/admin, без голосования. Перед применением — предварительный просмотр. Альтернативы можно скрыть или оставить; удаление из решения невозможно.
- Вопросик удерживается всеми актуальными незакрытыми решениями, определяющими посещение. Обычные задачи не удерживают вопросик; все связи показываются ссылками.
- При добавлении нового условия посещения в открытое решение статус want/без статуса становится maybe в той же транзакции; заметка сохраняется. Другие пользовательские статусы и visited не перезаписываются. Форма явно обозначает это как «Определяет посещение (под вопросом)».
- Противоречивые результаты не меняют статус автоматически. Статусы связываются по стабильным want/maybe/visited ID, не названиям; отсутствующий статус — конфликт, а не автоматическое создание.
- Попытка отдельной смены статуса на карте при незакрытом решении отправляет в календарь; заметки/ярлыки сохранять можно.
- Решение можно пересмотреть. Позднейшие изменения не откатываются автоматически. Скрытые вручную места сами не возвращаются.
- Зависимости мягкие: предупреждение не запрещает выполнить задачу. Сложные связи и вилки первоначально готовятся через чат, без конструктора условий.
- Переносы и пересчёт сроков выполняются через чат после анализа и согласования. На сайте нет формул и каскадного переноса. Внешние сроки помечаются отдельно, имеют источники.
- Карта ↔ календарь: прямые ссылки на карточку/запись, в карточке компактное превью связанных сроков. Несохранённые изменения защищены.
- В скрытых местах «Удалить всё», с подтверждением точного количества и состава. Доступ editor/admin.
- Удалённое место не восстанавливается из решения. Задачи/история остаются, ссылка становится «Место удалено», сохраняется только подпись связи.
- Справка обновляется с реализацией. Нет внешних уведомлений, ИИ внутри сайта, автопрокладки маршрута или бронирований.

## Хранение

Аддитивная миграция 0007: даты в trips; planning_items, planning_options, planning_item_places, planning_dependencies, planning_events. Места не копируются. Пользовательские поля и все существующие данные остаются.

planning_items содержит общие поля, тип, состояние, даты или UTC-моменты, исходный пояс, порядок, внешний фиксированный срок и источники, version. Связи мест могут относиться к варианту решения и иметь affects_visit. После удаления places FK становится NULL, подпись остаётся. Опции описывают только понятные действия (want при выборе, keep/hide при отказе), без произвольного исполняемого кода.

API использует существующие сессии, роли и защиту Origin. Изменения проверяют version. Предпросмотр вычисляет последствия на сервере и выдаёт подписанный снимком хеш; подтверждение сравнивает снимок заново внутри BEGIN IMMEDIATE. Все эффекты и история применяются атомарно. Повтор подтверждения не применяет эффекты второй раз. История хранит версии до/после для безопасного пересмотра.

Страница собирается текущим build-pages, все пути относительны для /taiwan-map/. Новые внешние зависимости не требуются. Существующий API карты расширяется без поломки старых клиентов. Экспорт включает календарь без секретов.

## Проверки и размещение

Перед миграцией production SQLite snapshot, проверка integrity/foreign_keys и репетиция на копии. Backend обновляется до frontend. Существующие unit, proxy и секреты не меняются. Проверить роли, одновременные изменения, откат транзакций, пересекающиеся решения, удаление, TZ/полночь, переполнение и мобильные темы. Выполнить все tests и build.

## Проверка первой реализации

- Автоматические проверки: API прав и версий, мягкие зависимости/циклы, пересечение и пересмотр решений, сохранение заметок, устаревший предпросмотр, полный откат при сбое, удалённые связи, точный состав массового удаления, идемпотентное наполнение, UTC/Taipei/DST, HTTP и Pages.
- Браузер: 360 и 390 px (перенос дат только на узком экране, отсутствие горизонтального переполнения), 1280 px (семь колонок недели), обе темы, перегруженный день «Ещё N», сохранение многострочной заметки, список/Сегодня, подтверждение выбора keep, переход календарь → конкретная карточка карты без повторного входа.
- Ресурсы проверены в собранной структуре /taiwan-map/ с версиями CSS/JS, а не только на Node root.
- Физический iPhone и реальное бронирование не использовались; напоминаний вне сайта нет. Время открытия продаж и плановые дедлайны различаются в описании. Требования для въезда и документов должны быть проверены отдельно для конкретного паспорта.
