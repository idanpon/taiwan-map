# Устройство Taiwan Map

Базовая архитектура после аудита 6 ноября 2026; модель 3 опубликована
14 ноября через PR #90 и отдельное обновление backend. Приложение рассчитано на одну
общую поездку и небольшую группу. Мультитенантность, отдельный сервер очередей,
ORM и frontend-фреймворк не требуются.

## Границы системы

GitHub Pages отдаёт HTML, CSS, ES modules, локальные библиотеки, manifest и
push-worker. Две страницы — карта и `planning.html` — используют общие форму
входа, шапку, темы, профиль и справку. Сборка не содержит каталога, базы,
учётных данных или личных экспортов.

Node.js 24 на VPS обслуживает API. SQLite — единственное рабочее хранилище.
В этом же процессе работает очередь Web Push. `server/index.mjs` связывает
HTTP, конфигурацию, базу, статические страницы для локального запуска,
необязательные снимки и завершение службы. GitHub Actions VPS не обновляет.

Опциональный [плагин ChatGPT](CHATGPT_PLUGIN.md) работает в том же Node/SQLite.
MCP и OAuth используют отдельную границу доступа; `assistant.html` обслуживает
подключение и подтверждение через сессию сайта. Внешняя модель и поисковый
API на сервер не добавлены. Функция выключена до настройки личного подключения.

## Данные и транзакции

Рабочая схема определяется последовательностью `drizzle/*.sql`. Название папки
историческое. Мигратор хранит SHA-256 каждого применённого файла в
`_app_migrations` и запрещает менять уже применённую миграцию. Новые изменения
схемы оформляются следующим SQL-файлом. Cloudflare D1, Drizzle runtime и
генератор не используются. Неполная старая TypeScript-схема и её metadata
удалены из рабочей ветки, история остаётся в Git.

- `trips`, `users`, `memberships`, `sessions` задают поездку и доступ.
- `places`, `categories`, `place_links` содержат сведения о местах.
- `statuses`, `user_place_states`, `state_events` сохраняют общие статусы,
  заметки, версии и историю. Активны три фиксированных ID, архивные определения сохраняют ссылки из истории. `trip-shared` — исторический владелец общего состояния.
- `place_ratings` хранит одну оценку на пару места и аккаунта. Среднее
  доступно в публичном каталоге, оценки по авторам проверяют роль. Для
  восстановления личных оценок используется SQLite backup.
- `planning_items`, варианты, связи, зависимости и события хранят общий план.
  Проживание и транспорт используют тот же ID и версии, поля маршрута транспорта хранятся в JSON, роли точек — в таблице связей. Удаление места оставляет подпись связи и запись плана.
- `trip_timezone_changes` задаёт точные моменты смены пояса. До первой смены
  действует Москва. Часы работы мест остаются местными для самого места.
- `planning_reminders`, `notification_preferences`, `push_devices`,
  `push_deliveries` содержат личные правила, устройства и очередь.
- `assistant_proposals`, `assistant_events` хранят личные предложения и
  квитанции, `assistant_oauth_codes/grants` — ограниченные подключения.
  `places.catalog_version` версионирует основные сведения отдельно от состояния;
  `coordinate_accuracy` / `coordinate_source_url` сохраняют происхождение координат.

Синхронный `transaction(db, callback)` открывает `BEGIN IMMEDIATE`, а внутри
другой транзакции — savepoint. Callback не может быть async. HTTP body и
сетевые запросы читаются до начала транзакции. Пакетный импорт календаря
использует ту же службу записи и одну внешнюю транзакцию: ошибка последней
записи откатывает также ранние записи, статусы мест, связи и историю.

### Модель 3 — данные, подготовка, время и варианты

Опубликована 14 ноября; рабочая поездка переведена в model3. Оболочка выбирается по модели
поездки и capabilities: model2 остаётся прежней, model3 — «Маршрут и подготовка».
`0014_route_foundation.sql` добавляет схему, оставляя `trips.planning_model=2`.
`0015_preparation_bookings.sql` расширяет её связями подготовки, исключениями
ночей, relative deadline rules и обратными ссылками истории на needs/bookings/services.
`0016_schedule_changes.sql` добавляет явное временное предшествование, overrides
переходов, запросы пересмотра и снимок условий утверждения placement.
`0017_route_options.sql` добавляет решения участков, условия вариантов,
неопределённые участки и результаты/prerequisites решений; options получают аудит.
`0018_booking_documents.sql` добавляет документы, связи с бронями/услугами,
приватные uploads/assets и leases хранения.
`0019_deadline_reminders.sql` добавляет личные якоря deadlines с сохранением
истории доставок. Этапы 1–6 опубликованы; прежние миграции
не переписывались. Границы визуальной проверки — в продуктовой спецификации.

Экран model3 разделён на `route-planning-{model,view,details,forms,editors,ui}.js`.
Общая проекция и командный слой используются сайтом, MCP и импортом;
`planning-presentation.js` форматирует один структурированный diff и причины.
MCP proposal с `planning_commands` хранит ID общего changeset и возвращает его
устойчивую квитанцию. Импорт model3 разносит preview/apply на два запуска.
`planning-deadline-view.js` используется UI, сервисом reminders и scheduler.
Отдельный `upgradePlanningModel` в одной транзакции переводит поездку в model3:
root scope, размещения посещений/жилья/транспорта, адресные связи мест, прежние
закрепления, одиночные цели задач и подтверждения существующего жилья.
Рабочие периоды задач, старые IDs/версии/заметки, история и напоминания сохраняются.
`planning_migration_refs` хранит техническое соответствие новых строк источникам.

В model3 размещение — источник плановых дат; прежние поля item служат проекцией.
Название/заметка общие. Потребности, услуги, подготовка, их реестр, проверка времени
и переносы, варианты и пересмотр решений доступны через model3 API.
Документы и скачивание доступны через API и новый UI. Capabilities и
completeness явно сообщают доступные проверки; `set_route_state` отдельно
фиксирует выполнение маршрута.

Все новые записи идут через закрытые команды, финальную проверку графа и один
синхронный сервис. Changeset личный до применения. Preview хранит выделенные IDs,
полный fingerprint источников, сроки и версии; apply повторно проверяет доступ,
актуальность и весь пакет, затем записывает данные, историю, напоминания и квитанцию
в одной транзакции. Повтор по ключу возвращает ту же квитанцию. Без preview разрешена
только правка общих текстовых полей, приоритета и ответственного.

`planning_revision` — монотонный счётчик изменений источников, а не число операций:
SQL-триггеры охватывают также прежние writers мест/поясов/связей. Один пакет может
увеличить его несколько раз. Полный fingerprint дополнительно включает личные
версии напоминаний; наружу выдаются свои подробности и только число чужих изменений.
Удаление места сохраняет подпись связи, увеличивает версии связи/родителя и делает
старый preview неприменимым. История операции доступна по `planning_event_refs`.

После явного перехода прежние HTTP/MCP/import не могут менять даты/связи/состояние
в обход нового слоя. Безопасный старый PUT текста перенаправляется в него.

Этап 2 расширяет тот же engine: `public/planning-preparation.js` проверяет
закрытые команды needs/tasks/bookings/services и конечный DAG,
`planning-readiness.js` вычисляет покрытие, применимость, ёмкость, ночи и
источники временных ограничений, `planning-targets.js` — относительные сроки.
`planning-impact.js` строит обратные ссылки истории по ID. Общие низкоуровневые
проверки вынесены в `planning-domain-common.js`. SQL/read-only реестр —
`src/planning-bookings.mjs`; отдельного writer или сервиса расчёта нет.
Подробный контракт и ограничения описаны в [PLANNING](PLANNING.md).

Read model, preview и apply используют одну проекцию; clock передаётся явно.
Policy version=6; ближайший expiry held ограничивает TTL preview, даже если
подтверждение в пакете удаляет этот expiry из будущего состояния. Идентичность
адресной проверки хранится как каноническая JSON-строка в историческом поле
place_match_context_hash: это сравнение полного контекста, не криптографическая
подпись. Сервер сам формирует значение при явном verify_place с пояснением.

Этап 3 объединён с прежними проекциями в `public/planning-projection.js`:
`planning-transitions.js` вычисляет дистанцию, контекст и эффективный gap;
`planning-schedule.js` — интервалы, ограничения/пины, конфликты и пределы
длительности; `planning-group-shift.js` — атомарное предложение сдвига в обе
стороны. `planning-schedule-commands.js` проверяет закрытые команды и условия
применения. Все модули чистые, без routing API/AI; сервер повторно использует
тот же расчёт внутри транзакции. Случайный порядок ID не разрешает временную
неопределённость. Stay участвует в дневной цепочке только явными моментами.

Пины услуги вычисляются из need→target/service и её условий, не копируются
в ручные constraints. `approved_context_json` хранит версии этих источников:
изменённый факт поставщика сохраняется, а прежний approved слот получает
requires_review. Request reschedule меняет намерение на tentative и связывает
открытую задачу обмена, сохраняя саму бронь. Точные acknowledgement keys
относятся только к конкретным последствиям; обычные конфликты ими не обходятся.
Transition context также хранит канонический JSON; часы/название не инвалидируют
его, точки/роли/качество/политика и явно связанная услуга — инвалидируют.
Автоматический gap не хранится как отдельное событие плана.

Этап 4 использует `planning-scopes.js` для единого разрешения активных ветвей,
явных requires/excludes и read-only сравнения. `planning-route-validation.js`
проверяет дерево, одного владельца item, глубину, доступность связей и общий DAG.
`planning-route-commands.js` обрабатывает создание/копирование, передачу владельца,
выбор/пересмотр и защиту принятого участка; `planning-route-effects.js` вычисляет
изменившуюся применимость и последствия реальных бронирований с точными ack keys.
Контекстный расчёт используется готовностью, временем, сроками, reminders и
совместимым чтением. Относительные сроки в comparison пересчитываются в локальной
проекции, без записи cache. Реальные услуги и завершённые задачи не копируются.

Решения поддерживают внешний и один вложенный уровень; сравнивается только явно
запрошенная комбинация. Item сохраняет один ID и общие заметки, placements — свои
времена/точки в опциях. Рабочий, принятый и просматриваемый варианты разделены.
Копирование листового варианта сохраняет общую подготовку, временные связи и
relative anchors; сложная неоднозначная связь требует явного mapping. Gap снижает
completeness, но не создаёт фиктивный временной слот. Группа останавливается на
границе scope. Legacy решения мест не переводятся в route_segment автоматически.
Подробности — [варианты участков](PLANNING.md#варианты-участков-и-пересмотр).

Этап 5: `server/document-storage.mjs` хранит закрытые неизменяемые bytes,
проверяет сигнатуры/hash и безопасные пути. `src/documents.mjs` обслуживает
авторизованные upload/content/finalize/download/Range, реестр и GC.
`src/document-assets.mjs` разделяет общую metadata и личные права привязки.
Storage key/байты/uploads не попадают в общий snapshot; чистый engine получает
только проверенные grants ready assets. `public/planning-documents.js`
выполняет create/replace/edit/attach/detach/archive в существующем changeset.
История использует отдельные document refs; связи документа не меняют версию
условий услуги, чтобы добавление файла не инвалидировало временной пин.

Native HTTP передаёт upload stream после обычной авторизации, не повышая общий
JSON-лимит. Квота резервируется транзакцией, запись upload защищена lease.
Файл синхронизируется и атомарно перемещается до DB ready; недоступный orphan
после сбоя безопасно финализируется повторно либо удаляется GC. Shared/history
references защищают assets от GC. Backup lease защищает SQLite snapshot и
копирование assets; `server/document-backup.mjs` сверяет manifest, SHA-256,
FK/integrity и восстанавливает только в новый каталог. Сохраняется существующий
Node/VPS, внешнего storage-сервиса нет.

Внутри atomic apply старые архивируемые связи обновляются перед новыми,
чтобы соблюдать частичные UNIQUE; FK проверяются при commit (defer_foreign_keys),
никогда не выключаются. История хранит точные команды, причины и before/after.
Разделение услуг сохраняет старую строку, копирует supplier deadlines на части
и требует явного allocation mapping там, где его нельзя однозначно сохранить.
Готовность не выводится из названий, числа аккаунтов или состояния задачи покупки.
Старые read-модели получают совместимую проекцию; новые плейсхолдеры жилья и
транспорта не маскируются под подтверждённые записи. Экспорт включает `planning_v3`.
Полный контракт и оставшиеся этапы — [в спецификации](../specs/2026-11-14-route-first-planning-architecture.md).

Сохранение карточки атомарно проверяет версии состояния и ярлыков. У видимости
и статусов собственные версии. Решения и смены поясов имеют предпросмотр с
хешем актуального снимка. Это проверка устаревшего состояния, не подпись и не
замена авторизации. Запись повторно проверяется внутри транзакции.

Предложения ChatGPT проверяются тем же путём записи в откатываемом savepoint.
Применение и квитанция составляют одну транзакцию; повтор возвращает результат.
Для предотвращения конфликтов используется хеш общей поездки, включая версии.

## Доступ и совместимость

Анонимный API перечисляет разрешённые поля явно. Он не формируется обрезанием
полного экспорта. Viewer читает частные данные и меняет только свои способы
входа/напоминания/устройства. Editor и admin меняют данные продукта; только
admin управляет участниками. `owner` сохраняется для начальной настройки
старой общей учётной записи, а не как новая продуктовая роль.

Bearer-сессии привязаны к API base, cookie-режим оставлен для совместимого
размещения. Сервер проверяет членство и отключение при каждом запросе.
Запоздалый отказ старой сессии не должен очищать более новую сессию клиента.
Пароль, Telegram и passkeys используют существующую выдачу сессий.

Старое чтение планировщика совместимо. Для полного плана новые клиенты передают `model=2`. Экспорт включает полный план. Маршруты редактирования каталога статусов закрыты. JSON-экспорт
не является полной резервной копией: он не содержит учётных данных, личных
правил напоминаний, устройств и очереди. Для восстановления всей системы
используется согласованный SQLite backup. Старый map-only importer отказывается
от экспорта с календарными записями или сменами пояса.
Личные предложения и OAuth-подключения также восстанавливаются только из SQLite.

## Сборка и сопровождение

`build-pages.mjs` обнаруживает верхнеуровневые JS/CSS/manifest в `public/`,
вычисляет версию и обновляет импорты модулей. MapLibre проверяется по manifest,
SimpleWebAuthn bundle — по установленному закреплённому пакету. Выходной
каталог внутри репозитория допускается только `dist/`; исходники, `.local/`,
Git и родительские каталоги защищены от очистки, включая символьные ссылки.

Проверки — Node test runner, локальные временные SQLite и HTTP, сборка Pages.
Мок push-транспорта проверяет очередь, но не доставку на физический iPhone.
Нативные Safari/Face ID также требуют проверки на устройстве.

Результаты этого аудита, оставшиеся риски и план выпуска — в
[AUDIT_REFACTOR.md](AUDIT_REFACTOR.md). Публикация и резервные копии — в
[DEPLOYMENT.md](DEPLOYMENT.md).

## Почему сохраняем эту архитектуру

Для одной общей поездки и нескольких/десятков участников обычные ES modules
и один процесс Node/SQLite покрывают текущие сценарии без отдельной очереди,
ORM и frontend-фреймворка. Чистые правила делятся между клиентом и сервером,
а критические права и транзакции остаются на сервере. MapLibre используется
напрямую, резервная подложка работает в том же движке — подробности и причины
в [MAP_THEMES.md](MAP_THEMES.md).

Общий план и состояния мест отделены от личных способов входа, устройств
и напоминаний. Подготовленное описание и пользовательская заметка хранятся
раздельно. Политика качества карточек — [PLACE_IMPORT.md](PLACE_IMPORT.md).
Изменение реального маршрута через чат не является автоматическим пересчётом
внутри сайта — [PLANNING_OPERATIONS.md](PLANNING_OPERATIONS.md).

Этот документ описывает реализованную систему. Существенное новое решение
сначала фиксируется кратко в spec с причиной, после реализации — в документе
соответствующего модуля. Отдельный реестр ADR не нужен, пока он не приносит
практической пользы. Порядок — [AGENTS.md](../AGENTS.md), формат —
[specs/README.md](../specs/README.md).
