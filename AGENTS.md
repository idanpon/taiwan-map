# Taiwan Map — правила работы

## Начало задачи

- Прочитай [HANDOFF](docs/HANDOFF.md): состояние, текущую работу и ссылки на нужные модули. Затем изучи связанный код и существующие спецификации из [specs/](specs/README.md). Карту компонентов и данных см. в [ARCHITECTURE](docs/ARCHITECTURE.md). На этом Mac учитывай `~/.codex/RTK.md`, если он доступен.
- Проверь `git status`, ветку и отличие от актуального main. Для параллельной работы используй отдельную ветку `codex/...` и worktree. Не перезаписывай чужие правки и не удаляй чужие checkout.
- Не полагайся на историю чата. Текущий запрос пользователя имеет приоритет; спецификация фиксирует ожидаемое изменение, модульная документация — реализованное поведение. При расхождении сверяй код и проверки; существенный продуктовый конфликт уточни, техническую неточность документа исправь.
- Рабочие данные поездки бери из актуального API/экспорта. Seed, архив и старые скриншоты не являются рабочей базой. Секреты, персональные экспорты и содержимое `.local/` не выводи в чат и не публикуй.

## Lightweight SDD

Идея → существенные уточнения → краткая спецификация → план → реализация → подходящая проверка → актуализация документов. Размер процесса соответствует задаче.

- **Мелкая правка UI, текста или локальный багфикс:** отдельная spec не нужна; достаточно понятного изменения и краткого отчёта.
- **Новая логика, изменение данных/прав/API или несколько сценариев:** до кода создай либо обнови один файл `specs/YYYY-MM-DD-short-name.md` по [шаблону](specs/_template.md). Запиши цель, границы, поведение, важные исключения, критерии приёмки и короткий технический план. Удали неприменимые секции.
- **Большое изменение:** только при реальной пользе выдели папку с `spec.md`, `plan.md`, `tasks.md`. Не создавай три файла автоматически, не вводи отдельный реестр решений или SDD-инструменты ради процесса.
- Уже ясный запрос является достаточным основанием для требований. Не требуй отдельного одобрения документа или каждой задачи плана. Не останавливайся после spec, если реализация входит в запрос. Просьба только обсудить/спроектировать не разрешает реализацию.
- У существующих функций остаётся модульная документация; не создавай задним числом подробные spec. Новая spec описывает изменение к текущему поведению и ссылается на него, а не копирует весь модуль.

## Самостоятельность и непрерывность

- Сам выбирай имена, структуру небольших модулей, CSS, подходящие проверки и другие обратимые технические решения в рамках согласованного поведения.
- Уточняй существенный продуктовый выбор, непонятные права/видимость, риск потери данных, несовместимость или значимую архитектурную альтернативу. Предложи конкретные варианты и рекомендацию; продолжай независимую часть работы.
- Работай завершёнными блоками. При паузе зафиксируй: что готово, что осталось, реальный блокер и следующий шаг. Если решение пользователя не нужно — продолжай сам, включая устранение ошибок и обновление документов.
- В незавершённой spec оставляй следующий конкретный шаг, чтобы работу мог продолжить другой чат. Временные ограничения среды не превращай в бесконечную настройку инструментов: используй разумный обходной путь, укажи его пределы.
- По завершении сообщи результат, реально выполненные проверки, отдельно предложенные/невыполненные проверки и состояние публикации. Можно назвать следующее улучшение, но не начинать новую фичу без запроса.

## Соразмерные проверки

- Полный набор тестов не является обязательным локальным ритуалом после каждой задачи. Выбирай минимальную проверку, которая обнаруживает вероятную ошибку; объясняй выбор кратко.
- Для документации достаточно сверки фактов, ссылок и diff. Для простой UI-правки — короткий просмотр реальной страницы на затронутом размере экрана. Для новой логики — подходящий существующий тест, небольшой регрессионный тест или API smoke test.
- При изменении общего интерфейса проверь затронутые мобильный/десктопный сценарии и темы, длинные строки и переполнение. При невозможности визуальной проверки честно предложи конкретный сценарий; макет не считать проверкой страницы.
- Для авторизации, прав, миграций, массовых операций и возможной потери данных нужны проверки соответствующих границ, отказов/отката и сохранности данных. Опасные записи не проверяй на production ради удобства.
- Быстрые доступные проверки выполняй самостоятельно; не пиши тесты, повторяющие реализацию без полезной проверки. Штатные обязательные проверки CI и выпуска сохраняются — [DEPLOYMENT](docs/DEPLOYMENT.md).
- Основные команды: `npm ci --ignore-scripts`, `npm test`, `npm run build:pages`, Node.js 24+ с `node:sqlite`. Установку повторяй при необходимости. Пути runtime текущего Mac — только `.local/LOCAL_SETUP.md`.

## Границы реализации и публикации

- Сохраняй текущую архитектуру: HTML/CSS/ES modules на Pages, прямой MapLibre, Node/SQLite и существующая служба VPS. Используй общие CSS-переменные и Lucide. Платные сервисы, второй движок карты и новые серверные компоненты требуют продуктового основания и запроса пользователя.
- Admin и editor равны внутри продукта; только admin управляет участниками. Viewer не меняет общую поездку, но управляет своими способами входа, напоминаниями и устройствами. Публичные и частные данные разделяются на сервере; правила — [PUBLIC_ACCESS_PASSKEYS](docs/PUBLIC_ACCESS_PASSKEYS.md).
- Сохраняй пользовательские заметки, несохранённый ввод, версии и состояние интерфейса. Не подменяй личные данные описанием из spec. Изменения реального маршрута и реестра подчиняются [PLANNING_OPERATIONS](docs/PLANNING_OPERATIONS.md).
- Не редактируй `dist/` вручную. Зависимости закреплены в lockfile, применённые SQL-миграции неизменяемы. Перед миграцией/массовой записью production сделай согласованный SQLite backup и проверь пакет на копии.
- Публикация frontend и backend раздельна. Действуй в пределах уже данного разрешения, не запрашивай его повторно; spec не является автоматическим разрешением менять production. Старые deploy/import-скрипты сначала сверяй с текущим кодом. Порядок — [DEPLOYMENT](docs/DEPLOYMENT.md).

## Документы после изменения

- Обновляй затронутый модульный документ и важные решения с их причиной. Новые ключевые возможности пользователя отражай в справке сайта.
- В spec отмечай фактический результат, отклонения и проверку; статус «готово» не означает «опубликовано» — доставку указывай отдельно. Устаревшую spec помечай заменённой со ссылкой на новую.
- HANDOFF хранит навигацию, короткое текущее состояние и незакрытые вопросы, а не копию всех правил или стенограмму чата. Подробности процесса находятся здесь, правила ведения spec — в `specs/README.md`, устройство системы — в `docs/ARCHITECTURE.md`.
